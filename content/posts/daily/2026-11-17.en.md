## Research lead one: whether successive screenshots need to be encoded from scratch

**StreamEmbed: Real-Time Indexing from Pixels for Screenshot Retrieval**, Dayoon Ko and colleagues, arXiv:2611.18516v1, submitted 2026-11-13 (UTC) [1].

The abstract concerns encoding and indexing visual memory as screen history arrives. It introduces StreamEmbed, an incremental visual embedding system, and asks whether pixels repeated in successive screen views need to be processed from scratch each time [1]. (General explanation added by this site: a vision encoder converts an image into representations a model can process.)

Our next reading questions concern which changes between screenshots require computation, which content can be reused, and whether retrieval still finds the views needed for a question. These questions require the full text. We do not report the abstract’s speed, accuracy, memory-use or device-test results, or conclude that screen recording can safely and completely replace human memory.

Short extract from the abstract:

> most pixels repeat within and across screenshots

## Research lead two: what information from a long task should remain available

**CarryOn: Learning What to Keep in Context for Long-Horizon LLM Agents**, Lihuan Li and colleagues, arXiv:2611.17808v1, submitted 2026-11-13 (UTC) [2].

The abstract considers multi-step tasks whose interaction histories keep growing. It introduces the CarryOn context manager, whose design pairs compact execution state with fine-grained, source-linked evidence, using a learned selector and adaptive retention policy [2]. (General explanation added by this site: context is the information a model receives for a processing step.)

Our follow-up reading questions concern the relationship between execution state, original evidence and later actions; the conditions for selecting information; and how task success and resource use are recorded separately. This is a reading checklist, not a finding that the retention policy is reliable. Without checking the full text, we do not repeat success rates, comparative gains, cost metrics or cross-task effects, or equate a shorter history with better decisions.

Short extract from the abstract:

> summaries can omit exact details needed for later actions

## Research lead three: arranging interactive and agent requests in a local server

**Superfluid: Local AI Server for Distributed LLM Inference**, Prabod Rathnayaka and colleagues, arXiv:2611.17753v1, submitted 2026-11-13 (UTC) [3].

The abstract introduces Superfluid, a server designed for local inference, and distinguishes concurrent interactive and agent use on one device from organizing multiple devices behind one interface. Its described single-device scheduler moves interactive requests ahead of agent work; across devices, machines serve copies of the same model and receive work according to measured speed [3]. (General explanation added by this site: inference is the process of a trained model taking input and producing output.)

Our next full-text questions concern request queues, records of delivered output during long runs, and how task completion and recovery are distinguished when devices join or fail. We have not checked an installed environment, code or deployment conditions. This issue does not repeat latency, throughput or failure-test results, claim installation on this site’s devices, or infer cost or privacy guarantees from the word “local.”

Short extract from the abstract:

> several agents share a locally served model with an interactive user
