A preregistered study of LLM code repairs finds that after a runtime or API migration, a release gate requiring all assertions to pass on typical inputs lets through 0.410 of wrong repairs over the complete repair space, and that one edge input written from the release note cuts this to 0.065 [1]. Another paper presents DictLLM, which compresses LLaMA-7B by 5.1 times without further training, with only a 2.9-point increase in WikiText-2 perplexity [2].

## Today’s news through the Unified Systems View

**Item 1: After a runtime upgrade, when AI-repaired code runs cleanly but returns wrong results, can an ordinary release check stop it?**

Background: The abstract says that after a runtime or API migration, a procedure repaired by a large language model can run cleanly yet return wrong results, and a release check on typical test inputs ships it [1].

In a paper posted on arXiv on 2026-11-05, "Accepted but Wrong: Silent Failures of LLM Code Repairs after API Migrations", four authors—Xiaobo Chen, Genliang Zhu, Ziyuan Wang and Chu Wang—report a preregistered study of 73 tasks covering 60 documented changes in CPython, Node.js and SQLite, in which every candidate is executed on the real runtimes against withheld contracts [1]. (General explanation added by this site: preregistration means publicly recording a study’s hypotheses and tests before running it.)

Why it matters: Over the complete repair space, the all-assertions gate on typical inputs released 0.410 of wrong repairs [1]. One edge input written from the release note cut this to 0.065, and to 0.061 on 15 unseen clusters; three inputs from a blind GPT-5.6-luna writer that never saw the program reached 0.070 [1]. Yet after 233 hard distractors that match the legacy output on typical inputs were added, 0.168 and 0.153 of the hard wrong programs still passed [1].

Where it sticks: Artifacts are available only from the authors on request; a blind AI audit flagged 34 contracts as stricter than their requirements, and dropping the disputed checks changed no verdicts, but class-label disputes remain open [1].

What to watch next: this is our own point to watch, not a conclusion of the paper: whether other teams, on other languages or runtime migrations, also find that release checks on typical inputs alone let through about four in ten wrong repairs, and that one edge input written from the release note brings this below one in ten.

**Item 2: Without retraining, can a large language model be made small enough for a phone?**

Background: The abstract says efficient deployment of large language models on mobile devices requires balancing performance with compute and memory constraints, and post-training compression is an effective approach that needs much less computation than in-training counterparts [2].

In a paper posted on arXiv on 2026-11-05, "DictLLM: Post-training Compression of Large Language Model with Dictionary Kernels" (entry states NeurIPS 2026), three authors—Jinho Park, Se Young Chun and Mingoo Seok—propose DictLLM, a dictionary-based scheme in which weight matrices within grouped layers are decomposed into a shared dictionary and layer-specific sparse coefficients, obtained directly from a pre-trained model without further training; storing one shared dictionary per layer group plus sparse coefficients reduces the memory footprint [2].

Why it matters: DictLLM compresses the original LLaMA-7B model by 5.1 times with only a 2.9-point increase in WikiText-2 perplexity, a 3.6 times higher compression ratio than the state-of-the-art low-rank method [2]. (General explanation added by this site: perplexity measures how uncertain a language model is when predicting text; lower is better.)

{{< industry-link item="2" industry="ai" side="cost" inference="a smaller model footprint matches lower actual hardware cost for on-device deployment" >}}The source reports the compression ratio and the matching perplexity increase [2], which maps to memory cost for deploying large language models on devices in this industry.{{< /industry-link >}}

Where it sticks: The abstract reports results on language modeling and zero-shot reasoning benchmarks, perplexity still rises by 2.9, and no speed or memory figures from running on a phone are given [2].

What to watch next: this is our own point to watch, not a conclusion of the paper: whether other teams, on larger models or real mobile devices, can keep a compression ratio of about 5 times with dictionary-style compression and no retraining, while holding the perplexity increase to about 3 or less.
