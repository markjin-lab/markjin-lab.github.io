LoopVQ compresses information that a language model keeps while generating text; it is designed for models that reuse the same layers over multiple steps [1]. Another method lets a model focus on selected parts of a long input without extra training; the authors report faster input processing and text generation [2].

## Today’s news through the Unified Systems View

**Item 1: After language models that reuse the same layers save parameters, can the key and value information kept while generating text fall below one bit per element while serving throughput still rises?**

Background: Looped transformers reuse the same layers across loop steps and match larger non-looped models with fewer parameters, yet each loop step still stores its own keys and values, so the key–value (KV) cache grows linearly with the number of loop steps and becomes the main memory bottleneck. The abstract says the KV cache of looped models is highly redundant along the loop axis and that loop steps differ substantially in their sensitivity to quantization [1]. (General explanation added by this site: a KV cache usually means the key–value state kept for already processed tokens so later steps can reuse it; vector quantization usually means compressing vectors into a few codebook indices to cut storage and bandwidth; BF16 is a 16-bit floating-point format.)

In a paper posted on arXiv on 2026-11-03, "LoopVQ: Sub 1-bit KV Cache Quantization for Looped Transformers", two authors—Minsoo Cheong and Sungjoo Yoo—propose LoopVQ, a KV-cache vector-quantization method for looped transformers that codes channels of multiple loop steps jointly and fine-tunes the codebooks to match the output of the full-precision model [1].

Why it matters: at 0.5 bits per element, LoopVQ outperforms existing KV-cache vector-quantization methods for standard LLMs on general, long chain-of-thought reasoning, and long-context retrieval tasks with Ouro and Huginn models; combined with TaSQ, it retains much of the BF16 accuracy even at 0.25 bits per element [1]. Implemented in SGLang, it nearly halves decode latency at a 32K-token context and raises peak serving throughput by up to 4.3× and 6.1× on the 1.4B and 2.6B Ouro models versus a BF16 baseline [1].

**Item 2: Can a training-free method that attends to only selected parts of a long input speed up both processing the input before an answer and generating text afterward by using larger semantic blocks?**

Background: The abstract introduces a training-free sparse-attention method that builds a prompt-specific key index, clusters keys into large semantic blocks that may group noncontiguous tokens, and lets each query select blocks by scoring centroids before attending to the original keys and values inside them. Queries that pick the same block are processed together so prefill stays fast; large blocks make centroid scoring and grouped processing cheap, so each query can attend to more tokens in the same time [2]. (General explanation added by this site: prefill usually means the stage that processes the input before an answer is generated; decoding usually means the later stage that generates the answer step by step; sparse attention usually means each query computes attention over only a subset of keys and values rather than over every position.)

In a paper posted on arXiv on 2026-11-03, "Coarse Semantic Blocks for Efficient Training-Free Sparse Attention", three authors—Sosuke Kobayashi, Shoichiro Yamaguchi and Seiya Tokui—evaluate two hybrid LLMs, Qwen3.5-4B and 35B-A3B, on one NVIDIA H200 [2].

Why it matters: including the cost of building and using the index, whole-model wall-clock speedups over dense attention are 2.3–2.4× for prefill and 1.7–2.0× for decoding at 512K tokens, and 2.9–3.0× for prefill at 1M [2]. The 35B-A3B model stays close to dense attention on five RULER tasks through 1M, on LongBench-v2 overall, and on MRCR through 256K; the 4B model loses accuracy mainly on multi-key retrieval, yet outperforms dense Qwen3.5-2B, whose latency is similar at 512K, on all three benchmarks [2].

**Item 3: Can a datacenter cut power without deferring interactive requests by only changing how queries are routed across model instances?**

Background: Growing energy use for large language model inference pushes datacenters to serve interactive workloads while also offering power-demand flexibility for safe grid operation. The abstract studies query routing as a way to allocate queries across language-model instances dynamically without deferring requests [3]. (General explanation added by this site: power-demand flexibility usually means how much electrical power can be raised or lowered over a short horizon.)

In a paper posted on arXiv on 2026-11-03, "Creating Power Flexibility in Datacenters via Query Routing", five authors—Shivam Patel, Bingqing Chen, Jared Fernandez, Guannan Qu and Gauri Joshi—develop an analytical framework that links arrival rates and sequence-length distributions to token iteration time, residence time, serving capacity, and instance power, and characterize feasible routing allocations and the matching power-demand flexibilities [3].

Why it matters: across four GPU platforms and language models from 1B to 70B parameters, the framework estimates achievable power flexibility with 2.8% mean absolute percentage error; on a real trace-driven simulation of a 10,000-H100 datacenter, flexibility reaches up to 16% of total power consumption, with 90% of the desired power reduction achieved within about 10 seconds [3].
